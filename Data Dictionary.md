# Data Dictionary — `support_tickets.csv`
 
Simulated support-ticket dataset, 6,000 rows, covering Jan 1 – Dec 31, 2025.
Generated by `generate_dataset.py` (seeded, fully reproducible — `SEED = 42`).
 
## Columns
 
| Column | Type | Description |
|---|---|---|
| `ticket_id` | string | Unique ticket identifier, e.g. `TCK-100042`. |
| `created_at` | datetime | Ticket creation timestamp. Weighted toward weekdays and business hours (9am–6pm-ish), with a small share of 24/7 off-hours volume. |
| `channel` | categorical | `Phone`, `Chat`, `Email`, `Portal`. Drives first-response speed. |
| `category` | categorical | `Billing`, `Technical Issue`, `Account Access`, `Bug Report`, `Feature Request`, `Onboarding`. Drives baseline resolution complexity. |
| `product_area` | categorical | `Mobile App`, `Web Dashboard`, `API`, `Integrations`, `Billing System`. ~1% missing (simulated data-entry gaps). |
| `priority` | categorical | `Low`, `Medium`, `High`, `Critical`. Loosely correlated with category (bugs/technical issues skew higher). Sets the SLA target. |
| `customer_id` | string | Simulated customer identifier (~2,400 unique customers; some submit multiple tickets). |
| `customer_tier` | categorical | `Free`, `Pro`, `Enterprise`. Drives SLA target tightness and handling speed. |
| `agent_id` | string | One of 24 simulated agents. |
| `agent_tenure_months` | int | Agent's tenure at time of dataset generation. Lower tenure → higher escalation risk, slightly slower resolution. |
| `first_response_minutes` | float | Minutes to first response. Driven by channel, priority (higher priority routed faster), and time of day (off-hours slower). |
| `resolution_hours` | float | Hours from creation to resolution. `NaN` for tickets still `Open`. Driven by category complexity, customer tier, agent experience, and a "backlog spike" mechanism that creates a realistic long tail (tickets stuck on engineering, customer non-response, etc.). |
| `sla_target_hours` | int | The SLA target for this ticket's priority × tier combination (e.g. Enterprise/Critical = 2h, Free/Low = 72h). |
| `sla_breached` | bool | `True` if `resolution_hours > sla_target_hours` (or, for still-open tickets, if elapsed time already exceeds the target — i.e. breaching in progress). |
| `escalated` | bool | Whether the ticket was escalated beyond first-line support. Probability increases with slow first response, higher priority, complex category, low agent tenure, and Free tier. |
| `escalation_reason` | string | Reason for escalation; empty string when not escalated (~82% of rows). |
| `reopened` | bool | Whether the ticket was reopened after resolution. More likely when the ticket was escalated, breached SLA, or is a Bug Report. |
| `status` | categorical | `Resolved`, `Resolved (Escalated)`, or `Open` (still in queue as of the data-pull date). |
| `csat_score` | float (1–5) | Post-resolution satisfaction score. Only present for resolved tickets with a completed survey (~55% response rate simulated). Inversely related to resolution time, escalation, breach, and reopening. |
 
## Built-in causal relationships (for your analysis to recover)
 
1. **Channel → response time**: Phone and Chat are fastest; Email and Portal are slower and more variable.
2. **Slow first response → escalation risk**: tickets with response times over 30–90 minutes are meaningfully more likely to escalate.
3. **Priority/tier → SLA target, not necessarily → resolution speed**: Critical/Enterprise tickets get faster handling in absolute terms, but their SLA targets are much tighter — so they can still show a *higher* breach rate than lower-tier tickets. This is a deliberate, realistic pattern worth surfacing in your writeup.
4. **Escalation → longer resolution**: escalated tickets pick up extra hand-off/review time on top of their base resolution time.
5. **Agent tenure → escalation & speed**: newer agents (<6 months) escalate more and resolve slightly slower.
6. **Category complexity → resolution time & breach rate**: Bug Report and Feature Request take longest and breach most; Billing and Account Access are quickest.
7. **Compounding effect on CSAT**: satisfaction drops the most when a ticket is *both* escalated and SLA-breached, more than either alone.
8. **Backlog spikes**: a random subset of tickets (more common for complex categories and non-Enterprise tiers) hit a long-tail delay simulating real-world stuck tickets — this is what actually produces most SLA breaches, rather than typical-case slowness.
